## Position

v0.4 is the incremental maintenance layer after v0.21/v0.3/v0.31:

```text
S0B
  -> S1
  -> S1 Index
  -> S2
  -> S2 Index
  -> Graph construction / graph query / visualization
```

The main problem is not ordinary CRUD over JSONL files. The main problem is:

```text
append new evidence
  -> detect affected derived material
  -> mark stale / superseded / deleted views
  -> rebuild or refresh affected upper layers
  -> preserve lineage and auditability
```

The design absorbs mature-system patterns before implementing local tooling:

- LlamaIndex-style stable document ids and source-to-derived-node mapping;
- Mem0-style add-oriented extraction/intake where possible;
- Basic Memory-style search-before-write and active-status filtering;
- LangGraph-style namespace separation;
- Letta-style compact current working view;
- LightRAG-style delete/update impact propagation.

## Core Principle

S0B is the lowest stable evidence organization layer. It should be append-only
for incremental add operations.

For delete/update operations, do not physically rewrite old S0B rows as the
first design. Instead:

```text
new operation
  -> find affected lower/upper artifacts
  -> mark old derived rows as stale/superseded/deprecated/deleted
  -> publish a new latest view
```

This keeps the system auditable and avoids silently destroying evidence
lineage.

## Layer Questions

### S0B

Current intended behavior:

- add-only for new raw/source material;
- source update/delete represented as an operation, not direct mutation;
- old source/S0B units can be marked inactive, superseded, deprecated, or
  deleted in the latest view;
- physical deletion is deferred and should require an explicit hard-delete
  policy.

Open questions:

- What is the stable unit id for S0B incremental tracking?
- Does a source update create a new source version, a new S0B batch, or both?
- How do we represent "this old unit should no longer participate in query"?
- How do we keep raw backpointers when source material is superseded?
- Should S0B emit a separate `s0b_latest_view.jsonl`, or should the latest view
  be computed from operation logs?

### S1

S1 incremental work consumes new/active S0B units. It should not simply append
new memory units and ignore older ones. It must compare new S0B-derived S1
material against existing active S1 material.

Important comparison questions:

- Does the new S1 unit duplicate an existing active unit?
- Does it strengthen or refine an older unit?
- Does it weaken, contradict, or supersede an older unit?
- Does it introduce a new evidence path for an existing unit?
- Does it refer to an inactive/deprecated source?

Current intended behavior:

```text
new S0B units
  -> route_s1
  -> S1 build/proposal lane
  -> compare against active S1 latest view
  -> emit S1 delta decisions
```

## Non-Goals For First v0.4 Slice

- No physical hard delete.
- No silent in-place JSONL mutation.
- No graph truth writes.
- No S3/support checker.
- No permanent graph backend decision.
- No automatic entity merge.
- No large-scale live run before small-workspace consistency is proven.
